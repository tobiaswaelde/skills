# Specialist execution boundaries

These checks specialize the active coding task; they do not start a second delivery workflow. Read the target project's instructions and relevant coding-guidelines first. Reuse the current scope, issue, task checklist, branch/worktree, and valid approvals. Use [native interactive decisions](interactive-decisions.md) for material missing choices. Discover actual scripts, tools, versions, providers, and test fixtures rather than requiring a universal stack.

- An inspection or assessment request is read-only. Implement fixes only within requested and approved scope, following the active workflow's implementation/commit/PR gates. A discovered gap is not permission for unrelated cleanup, a migration, or a new tool installation. Leave existing intentional project conventions intact unless a change is agreed.
- Use existing confirmed local/disposable test environments and synthetic data for executable checks. Identify the target and reset/cleanup boundaries before state-changing tests; do not assume a database is disposable merely because a URL uses localhost or its variable name contains TEST. Keep production/shared-system mutations and destructive operations outside these specialist assessments unless separately authorized by the appropriate execution workflow.
- Never expose secrets, tokens, session state, private customer records, or connection strings in logs, screenshots, fixtures, or reports. Use redacted identifiers and synthetic test identities. Stop dependent operations when the target or authorization is unclear while continuing independent code inspection.
- Base findings on a concrete artifact or reproducible behavior. Distinguish observed failures, supported risks, and missing evidence. Record the tested revision, relevant environment, command/scenario, result, and remaining gap; skipped or unavailable checks are not passes. Use the project's supported tools and version-matched primary documentation for unfamiliar behavior.
- Reports follow the user's language and concise Changed/Tests/Notes preference; repository artifacts use en-US unless project/user instructions differ. A report or an internal checklist grants no merge, release, publish, or deployment permission. Changesets/Version Packages release PRs remain manual.
